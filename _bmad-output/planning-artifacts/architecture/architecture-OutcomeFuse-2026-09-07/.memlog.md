- (decision) Control boundary = mediated (option C). A pure framework-agnostic governor core sits behind a narrow port; a host adapter proposes a step, receives a verdict, and is responsible for applying it including termination. Alternatives weighed and rejected: (A) interception only - wrap the model client and tool registry, cheapest integration and truest to FR50, rejected because the sufficiency stop becomes a signal the host may swallow, which would refile the product's headline event stop-sufficient as halt-exhausted, and because FR98's gate-before-any-terminal-halt cannot be guaranteed by a party that does not own the halt; (B) governor drives the loop - makes FR1, FR23 and FR98 trivially true, rejected because it is precisely the re-architecture FR50 promises not to require and it breaks the UJ-4 adoption story. C subsumes both as adapter strategies behind one port. Binds F11 and every mechanism. Prevents the divergence where one host integration honours a deny by raising and another by returning a sentinel, so the decision record cannot be compared across implementations. Known cost accepted: the adapter is load-bearing and untrusted, so an adapter conformance suite is now required work that the PRD did not scope.
- (decision) Paradigm = ports-and-adapters (hexagonal) with an append-only decision log as the system of record. The governor core - Outcome Contract, Budget Ledger, Quality Gate, Policy, Loop Fuse - is pure and performs no I/O; model, tools, record sink, clock, approval channel and gateway metering are ports. Run state is a fold over the decision log, not a separate mutable structure kept in sync with it. Rationale: NFR8 domain neutrality, NFR10 independent disableability, FR62 per-mechanism ablation and FR68 re-executability fall out of the paradigm instead of being bolted on; FR5's record-before-effect is literally write-ahead logging, and FR6, FR55 and FR68 require run state to be reconstructible from the record without re-invoking a model, which is event sourcing. Consequence: replay, audit and the harness are three readers of one log rather than three features, a material simplification for a solo one-month build. Alternatives rejected: record-as-byproduct, which makes FR5's ordering guarantee a discipline rather than a structural fact and forces two representations of run state to be kept honest; pipes-and-filters, which models the seven mechanisms but not the policy-above-mechanisms subordination that FR4 makes central.

- (decision) Streaming is barred on any run that produces a reportable figure. Forced by a verified fact: Azure APIM llm-token-limit estimates BOTH prompt and completion tokens when stream is true, and llm-emit-token-metric produces inaccurate counts on interrupted streams. Streaming is therefore a demo-only affordance structurally outside the evidence path. It costs nothing in the submission because FR72 already replays recorded runs rather than streaming live. Binds F13, F15, F16 and the ModelPort. Prevents the divergence where the harness and a host adapter disagree about whether a streamed run is admissible evidence.

- (decision) One decision lane per run. The governor takes decisions strictly one at a time; the host may execute approved steps in parallel. Budget is RESERVED at decision time and SETTLED at completion, so FR13's reserved field is enforceable rather than advisory. Closes a real double-spend hole neither the PRD nor either mechanism catches in isolation: LangGraph and Microsoft Agent Framework both issue parallel tool calls, and two concurrently proposed steps can each pass FR16 affordability against the same remaining, breaching the ceiling FR2 ranks above nearly everything, with no individual rule violated. Also required by the paradigm - an append-only log as system of record needs a total order, and concurrent decisions do not have one. Rejected: an atomic compare-and-set ledger permitting concurrent decisions, which fixes the arithmetic but leaves the log partially ordered and replay non-deterministic; and forbidding host parallelism, which would be a re-architecture demand FR50 forbids. Accepted cost: NFR1 decision latency now sits on a serial path, and a host batching ten parallel calls receives ten sequential verdicts before any execute - so per-decision latency must be measured against batch width, not only per step.
- (decision) Record store = SQLite, one database file per run. Chosen for stdlib availability, zero operations, genuine queryability for FR54, and archive-or-delete-by-file which satisfies NFR12 retention without extra machinery. Append-only is enforced as a discipline - the record writer exposes append only, and no UPDATE or DELETE statement may be issued against the decision table - rather than being a structural property, and that is the accepted weakness of the choice. Rejected: JSONL alone, structurally append-only but turning FR54 queryability and the harness's cross-run joins into hand-written scans; JSONL-as-truth with a derived SQLite index, the strongest story but one more moving part than a one-month solo build should carry. Four consumers read this store - F12 query and export, F13 proof-card computation FR97, F14 replay FR72-FR76, F16 submission figures FR82 - so the store and its schema have exactly one owner.
- (decision) Redaction happens at the port, not at the record sink. Raw prompts, tool arguments and tool results never leave the adapter that produced them; everything crossing inward into the governor core is already redacted, hashed or reduced to a derived value. NFR5 and FR56 therefore become structurally true - the core cannot leak what it never held - instead of a rule someone must remember at every write site. Rejected: redact-at-the-sink, which is simpler for mechanism authors but makes every in-memory structure sensitive, lets a stack trace or debug log leak, and reduces NFR5 to a discipline. Binding consequence on FR6: the model-derived inputs a decision consumed must be recorded as DERIVED VALUES - complexity and confidence estimates, rubric scores, planner envelopes, marginal-value estimates, canonicalized tool keys, content hashes - never as raw text. That is a real constraint on what any mechanism may pass upward, and it is also what makes FR55 honest, since the reconstruction of why a run stopped is then possible without the transcript ever existing in the record.
- (decision) One canonicalisation function, owned by the core, serves all four hashing concerns: FR10 contract identity, FR29 tool-call keys, FR65 rubric and answer-key freeze, FR64 baseline-configuration freeze. Contracts are authored as YAML because FR12 makes them hand-written and comments matter, validated by a pydantic 2.13 model, then serialised to canonical JSON with sorted keys, no insignificant whitespace and normalised number forms, and hashed with SHA-256. No component may hash a structure by any other route. Prevents the silent divergence where the Tool Governor canonicalises dict key ordering one way and the harness another - nothing fails loudly, you simply get cache misses that should have been hits under FR30 and FR31, or a spurious FR65 drift refusal on a rubric that never changed. Both alternatives are individually reasonable in code review, which is exactly why the choice has to be fixed above the code.
- (decision) Mechanism contract fixed as three single-writer rules, turning FR4 and the section 1.5 principle from a stated intent into something a builder cannot accidentally violate. (1) A mechanism is a PURE ADVISOR - it receives read-only state and returns a proposal consisting of a suggested action, an estimate and a candidate decision_reason; it never mutates run state and never calls a port. (2) The Policy is the sole component that converts proposals into a decision. (3) The Ledger is the sole writer of spend, and debits from the recorded outcome of a port call, never from a mechanism's self-report. Prevents the constructible divergence where the Tool Governor debits its own cache-miss spend while the Context Governor returns a capsule and lets the caller debit - both obey FR4 as written, yet FR15 per-mechanism attribution then carries two different meanings and FR62's ablation compares numbers computed differently, which would invalidate the only thing that makes a headline figure publishable. Consequence: NFR10 falls out for free because DISABLED MEANS NOT REGISTERED - no mechanism carries an enabled branch, FR62 ablation is a registry change rather than a code path, and an ablated configuration is therefore identical to a cut one rather than merely similar to it.
- (decision) Operational envelope decided rather than left silent. The MVP has no server deployment: an in-process library, a CLI harness, a generated local viewer, plus one managed slice - F15 gateway metering through Azure APIM. Model traffic routing is an invariant forced by fairness, not a convenience: BOTH ARMS OF ANY COMPARISON USE THE SAME ROUTE, and the route is recorded in the run manifest. Reportable runs route through APIM so FR78's gateway metering is real; local development and demo runs may go direct and are structurally barred from producing a reportable figure, the same bar the no-streaming rule applies. Grounds: FR64 freezes the baseline configuration and the harness refuses a comparison when the executing configuration differs - the route IS part of that configuration, so a governed arm through APIM against a baseline arm going direct introduces latency, retry-behaviour and token-accounting differences that have nothing to do with the governor, breaking section 8.1 baseline fairness by construction. Accepted cost: a working APIM instance is now a critical-path dependency before the evaluation set can be executed. Environments are local development and a single Azure subscription hosting the APIM instance; no staging tier exists and none is warranted at MVP.
- (decision) F14 side-by-side view = a STATIC HTML artifact generated from the decision record by the harness, one self-contained file per comparison, embedding the replay timeline, ledger state at each decision, the rendered proof card and enough of the record to satisfy FR76 drill-down offline. User delegated the choice; recorded here with its grounds. - (decision) A contract SHALL NOT execute code. FR8's executable deterministic verification method is implemented as a CLOSED, PROJECT-OWNED VERIFIER REGISTRY: the contract selects a verifier TYPE and parameterises it declaratively - field-present, type-is, numeric-range, set-membership, regex-match, exact-match-against-answer-key, citation-resolves - and nothing resembling code crosses the contract boundary. Security ground: the obvious implementation, a contract naming a Python import path or carrying an expression that is evaluated, is arbitrary code execution driven by a data file, in a product whose position is that platform teams hand contracts to agent owners. That is remote code execution wearing a configuration costume. Correctness ground: it also breaks FR10 - a contract is immutable for a run and carries a stable hash, but a verifier that is a reference to code can change while the hash does not, so the attestation would cover something that was never pinned. Consequences that fall out for free: FR8's rejection of a mandatory criterion with no executable verifier becomes a registry lookup; the contract hash covers the entire verification semantics; and the FR21 reference-backed versus constraint-backed label is determined by which registry entry was used rather than being separately asserted. Rejected: a sandboxed expression language, more expressive but it makes the project the owner of a sandbox, which is not affordable in a one-month solo build. Accepted constraint: a criterion for which no verifier type exists cannot be mandatory - which is FR8's own rule, not an additional restriction.
- (decision) Shadow mode is a SEPARATE EXECUTION DRIVER, not a mode flag inside the Policy. The Policy is unchanged and always decides as if enforcing; a shadow driver takes each decision, records it, and declines to apply it, letting the host proceed. Prevents the failure the mode-flag design guarantees: a shadow branch inside the Policy and inside every mechanism, and - because FR91 exempts shadow mode from fail-closed - a shadow branch inside the fail-closed paths too, which places a conditional in the most safety-critical code in the system, on the branch that must never fire in production and is therefore the least exercised by tests. Consequences: FR91's exemption becomes the single statement that the driver does not apply halts, located in one place; and FR96's first divergence is a fact the driver OBSERVES - the first decision it declined to apply - rather than something a mechanism must compute and could compute differently. Accepted cost: during a shadow run the real ledger and the estimated counterfactual ledger both exist, so the estimated one must be structurally prevented from contaminating a reportable figure, which FR49 and FR83 already require and FR106 narrows to synthetic and replayed workloads.
- (decision) Human approval is an ApprovalPort whose only MVP implementation is a SCRIPTED SYNTHETIC DECIDER driven by the case definition - approve, deny, or never respond. The port is real, so FR89's fail-closed-on-unavailable path is genuinely exercised rather than asserted. Ground: FR100 requires synthetic cases for approval timeout under BOTH on_timeout postures, and a scripted decider is the only implementation that can produce those cases deterministically; a blocking interactive prompt would make FR100's timeout cases untestable without a person sitting in front of the harness, inside a harness whose entire value is reproducibility under FR68. Rejected: an interactive CLI prompt as the only implementation, which demos well but makes the approval cases manual; and building both a scripted and a CLI implementation, deferred as an optional demo affordance rather than committed scope. Availability is defined at this port: the channel is unavailable when the configured decider cannot be reached or does not respond within approval_timeout, and FR95's default triple then applies.
- (decision) The decision-record schema is project-owned and version-stamped, and the decision_reason registry (FR104) is a single owned module - one enum of stable codes with declared families, plus a registry version written into every run. OpenTelemetry GenAI attribute NAMES may be borrowed as a naming convention where they fit, but the schema SHALL NOT depend on that specification. Verified ground, 2026-09-07: the GenAI semantic conventions are still Experimental, have moved out of the main semconv repository into open-telemetry/semantic-conventions-genai, that repository has NO published releases, and gen_ai.usage.input_tokens and gen_ai.usage.output_tokens are both marked Development rather than Stable. FR104 promises that a published code still means what it meant when it was written; delegating that promise to an unreleased external specification would let a third party revoke it. Every decision row carries the schema version and the registry version, so an old record remains readable after either evolves.
- (decision) Every run opens with a RUN MANIFEST written as the first entry of its decision log, and no comparison may be published without one. The manifest carries: run identifier; mode (governed, baseline, shadow); contract hash; rubric and answer-key hash (FR65); frozen baseline-configuration hash (FR64); case-set identity and whether it is calibration or evaluation (FR102); model identifiers with provider versions; the pinned cost-table version used to convert tokens to estimated cost; the route (APIM or direct) and therefore whether the run is reportable; streaming disabled; enabled-mechanism registry with versions, which is what FR62 ablation varies; adapter identifier and version; governor code version; and the random seed and any sampling parameters. This single artifact is what makes FR68 re-executability, FR64 and FR65 drift refusal, FR102's preregistration-before-execution ordering check and FR62's per-mechanism attribution all mechanically checkable rather than trusted. Prevents the divergence where the harness, an adapter and the viewer each decide independently what constitutes a run's configuration - a disagreement that would surface as an unexplainable difference between two runs that were believed identical.
- (decision) Adapter conformance suite is committed work, not optional. Because the mediated boundary makes the host adapter responsible for APPLYING a verdict including termination, a sloppy adapter can silently fail to honour a deny or a stop and the system will report a plausible run that never obeyed its own policy. The suite is a fixed battery of scripted scenarios each adapter must pass - deny honoured, substitution applied, approval pause observed, sufficiency stop terminates, fail-closed halts, shadow decisions not applied - asserted against the resulting decision log rather than against adapter internals. An adapter that has not passed the suite SHALL NOT produce a reportable run, which is the same bar applied by the no-streaming and direct-route rules. This is work the PRD did not scope and it grows with the third committed framework. Prompt-injection posture recorded alongside: tool output reaches model-derived advisors - the FR20 rubric signal, the FR22 advisory tool-quality signal, the marginal-value estimator - so poisoned tool content could try to induce an early sufficiency stop. The architecture already bounds this rather than needing new machinery, because FR20 makes deterministic criterion-level validation the authoritative gate, FR22 bars the model-judged signal from altering the verdict, and the closed verifier registry means no contract-declared check can be steered by tool content beyond the declared extraction. The bound must be stated so it is maintained deliberately rather than accidentally.
- (decision) The tool cache is RUN-SCOPED and process-local. No cross-run, cross-process or persistent cache exists in the MVP. FR30 already limits reuse to the scope of a single run; making that a structural property rather than a policy setting is what discharges NFR6 cache isolation trivially, since a run belongs to exactly one tenant and one use case and cross-user reuse is therefore impossible by construction. Prevents a builder reasonably concluding that a persistent cache is a free win - it is not: a cross-run cache would make FR68 re-executability depend on cache warmth, would make two supposedly identical runs differ, and would put NFR6 tenant partitioning on the critical path of the most performance-sensitive component. Deferred rather than rejected: a persistent cache is a legitimate post-MVP lever, and the deferral condition is that it requires a tenant-partitioned key and a story for how FR64 and FR68 stay honest when cache state varies between runs.

- (decision) Q-C RESOLVED for MVP synthetic data, under retention profile mvp-synthetic-v1. Two tiers, because AD-5 already split the data by sensitivity and the lifetimes should follow that split rather than fight it. Raw synthetic evidence is retained 60 calendar days from a harness-owned run_closed_at, set when the run reaches a terminal state, completes normally, or is explicitly abandoned; expiry is run_closed_at plus 60 days and is never derived from filesystem modification, access or copy time. Redacted decision records and proof artifacts are retained 180 calendar days from campaign seal. No ad hoc per-run extension exists - if raw evidence expires before an FR69, FR70 or FR71 assessment completes, the frozen case is re-run rather than the period being quietly stretched, which keeps the retention rule from becoming negotiable at exactly the moment someone wants it to be. Deletion unit is the complete per-run evidence root evidence/<run_id>/ covering deliverables, capsules, raw tool outputs, suppression re-execution artifacts, compression-fidelity artifacts, generated blind-review packets and temporaries; no record-by-record deletion is required. The retention command selects from the manifest, refuses a directory whose declared run_id does not match its manifest, closes handles, deletes the tree, verifies absence, and writes a CONTENT-FREE deletion receipt - run_id, evidence_manifest_hash, retention_profile, scheduled_expiry_at, deleted_at, result - into a separate append-only campaign retention manifest, explicitly NOT appended after the sealed terminal row, because that would alter the run seal AD-16 established. This is logical deletion appropriate to synthetic data and is not claimed as cryptographic erasure or media sanitisation. Access is an explicit matrix rather than a convention: driver writes its own run's evidence; harness reads and generates FR69-FR71 artifacts; the retention command holds delete-plus-manifest-status only; the blind-review renderer holds a read-only evidence capability plus the contract and no decision-record, verdict or manifest capability; and quality verifiers, host adapters, the static viewer, the submission generator and the model and approval adapters have NO access at all. The evidence root stays gitignored and out of generated HTML, the submission archive, test snapshots and application logs.
